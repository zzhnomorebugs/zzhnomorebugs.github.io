Protein generation at scale

01 Turn large-scale sequence data into usable generation conditions

The project aims to train models that generate protein sequences, providing a foundation for subsequent candidate screening and studies of target properties. The internship work focused on implementing a working training pipeline and addressing the preprocessing, storage, and data delivery challenges of a large corpus.

  1. Input: Protein sequences and MSAsExtract amino acid distributions at each aligned position to condition generation.
  2. Training: Learn sequence generationRun short controlled comparisons, select modules and configurations, then start full training.
  3. Output: Candidates for screeningUse subsequent evaluation and screening to study sequences with target properties.

This work was conducted at Shanghai Artificial Intelligence Laboratory. With more than 30 million sequences, integrating an algorithm into a model is only part of the task: repeatedly scanning the raw data to find each MSA, or saving fully expanded intermediate representations, can make preprocessing and storage themselves a limit on training.

From aligned sequences to a profile

02 Summarize aligned sequences as frequencies at each position

A multiple sequence alignment (MSA) places related sequences into common aligned positions. Counting amino acid classes within a column describes the variation and conservation at that position in the input alignment.

Suppose an MSA contains \(N\) sequences of aligned length \(L\), with \(K\) classes. Convert each class into a one-hot indicator, sum over the sequence dimension, and divide by \(N\):

\[C_{j,a}=\sum_{m=1}^{N}\mathbf{1}\!\left[x^{(m)}_j=a\right],\qquad P_{j,a}=\frac{C_{j,a}}{N}.\]

\(C\in\mathbb{N}_0^{L\times K}\) stores integer counts, while \(P\in[0,1]^{L\times K}\) is the profile. The class vocabulary and alignment processing rules must remain consistent between preprocessing and training data loading.

In this example, A has frequency 1 at the first position, meaning that all input sequences agree there. At the second position, C and T each have frequency 0.5, so generation still requires a choice informed by the conditions and sequence context. A profile provides marginal frequencies at individual positions; it cannot by itself express dependencies between positions or require the model to copy each column.

Index once, process in parallel

03 Locate each MSA before computing profiles in parallel

The first step in efficient preprocessing is to reduce repeated searches. Finding the MSA for a target protein should not require scanning every record from the beginning of the raw data each time.

Position indexing: Separate lookup from parsing

Preprocessing first builds an index from record identifiers to storage positions. For a target, the program looks up its position, then reads and parses the corresponding MSA record. The initial scan builds reusable location information for subsequent target retrieval.

Position index data flow · Pseudocode

position = record_index[target_id]
msa_record = read_record_at(position)
aligned_tokens = tokenize(msa_record)
counts, msa_count = aggregate_by_position(aligned_tokens)

Here, position abstracts the location of a record; the essential point is to avoid repeated scans from the beginning. The index locates the record, while parsing and tokenization convert its contents into sequences ready for counting. Each stage can be optimized separately.

Partitioning: Distribute independent targets across CPU nodes

Partition the target records and process the partitions concurrently on multiple CPU servers. Each task handles lookup, reading, parsing, and profile counting, allowing the large corpus to be preprocessed in parallel and stored as HDF5 data for training.

Tokenization: Choose an implementation through timing comparisons

After lookup is accelerated, sequence parsing and token conversion still run tens of millions of times. Different tokenizer processing methods were timed and compared in a table to select a more efficient implementation. The selected method achieved approximately a 40% speedup over the default method, specifically in the tokenizer stage of preprocessing.

Store counts, normalize on load

04 Store integer counts and compute frequencies when loading

The numerator of a profile is already an integer. Because frequencies can be recovered from counts and the number of aligned sequences, every position and class need not be stored permanently as a floating-point probability.

  1. Aggregate: MSA → C and NSum one-hot indicators along MSA depth to obtain class counts at each position.
  2. Store: Integers in HDF5Save compact integer counts and the sequence count required to recover frequencies.
  3. Load: C / N → ProfileConvert to floating point and normalize before supplying the generation condition.

Storage and loading data flow · Pseudocode

# Offline preprocessing: C has shape [L, K]
C = sum(one_hot(msa_tokens), axis="msa_depth")
save_h5(integer_counts=C, msa_count=N)

# Training data loading: recover frequencies when needed
C, N = load_h5(record_id)
profile = to_float(C) / N

The stored values are exact counts, rather than probabilities truncated to integers. Provided the integer type can represent the largest count, \(C/N\) recovers the corresponding empirical frequencies. The required bit width therefore depends on MSA depth and the range of the counts.

Table 1 · Representations of an MSA, integer counts, and a floating-point profile
RepresentationLogical shapeInformation retainedRole in the pipeline
Aligned MSA tokens\(N\times L\)The class at each position in every sequenceInput to offline counting
One-hot expansion\(N\times L\times K\)Class indicators for individual sequencesIntermediate representation explaining aggregation
Integer counts C + sequence count N\(L\times K\) + one denominatorOccurrences of each class at each positionPersistent HDF5 storage

Aggregation removes the MSA depth dimension. For the same \(L\times K\) shape, compact integer storage further reduces the bytes per element. These are two distinct storage improvements: one changes the statistical representation retained, while the other changes its storage type.

Compare before the full training run

05 Select modules with short experiments before full training

A full training run for a larger generative model consumes substantial resources. Early experiments therefore used a 150M model for short runs, holding other training settings constant and comparing loss at the same step count before selecting modules and configurations.

Training studies: How time embeddings enter the network

The time variable describes the current noise stage. A time embedding encodes this information and injects it into the network. Even with the same backbone and objective, the injection method can affect how the model learns to denoise, making it a useful module to compare.

\[e_t=\operatorname{TimeEmbed}(t),\qquad \widehat{x}=f_\theta(x_t,e_t,P).\]

This expression summarizes three inputs: the current state \(x_t\), the time condition \(e_t\), and the MSA profile \(P\). Experiments changed the time-conditioning implementation while keeping the other settings constant, comparing loss and convergence trends at matching training steps. These comparisons apply to configurations with the same training objective and loss definition.

Sampling studies: Compare algorithms and hyperparameters separately

Once trained, the model still requires iterative updates to generate sequences. Separate comparisons therefore explored diffusion sampling algorithms and their hyperparameters, studying update rules and control options during generation. Training loss informs training configuration choices; sampling algorithms must be examined during generation.

Data delivery: More workers do not always mean higher throughput

Training also exposed failures and reduced loading efficiency when the number of data-loader workers was too large, alongside GPU utilization that could not reach the desired level. Fitting the data on disk is therefore only one requirement: data must also arrive fast enough to keep up with computation, and loading concurrency needs to be adjusted against observed efficiency.

Data access, CPU processing, and model computation jointly determine training progress. Moving parsing, token conversion, and profile counting into offline preprocessing lets training load counts and normalize them directly, reducing repeated computation of the same statistics.

Engineering contributions

06 Connect data processing and controlled experiments to final training

The main contributions were in implementing the generative modeling pipeline: locating large-scale MSA records, computing their statistics, storing them compactly, and supplying them to training, while using early controlled comparisons to reduce trial and error in full training runs.

The common approach was to replace repeated searches with position indexing, distribute independent counting tasks across CPU nodes, store recoverable frequencies as integer counts, and evaluate training and sampling choices in their respective comparison workflows. Together, these steps connected large-scale data processing with a working model training pipeline, providing a foundation for subsequent candidate generation and property screening.
