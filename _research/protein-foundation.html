Protein generation at scale

01 Make large-scale MSA data support generative model training

This work at Shanghai Artificial Intelligence Laboratory trains protein sequence generators conditioned on multiple sequence alignments (MSAs). The central engineering task is to connect processing, storage, and delivery of data covering more than 30 million sequences with model experiments in a working training pipeline.

The engineering principle: Move reusable work before training

Index record positions once, compute MSA statistics offline, and recover profiles during training. On the model side, run short comparisons before full training, giving data preparation and model iteration clear, separate roles.

From MSA conditions to sequence generation

02 How does the model use MSAs to generate new protein sequences?

An MSA aligns related sequences. Counting amino acid frequencies within each column produces a profile describing which classes occur commonly at that position. The generator combines this condition with the current state and time to propose candidate sequences step by step.

Model design: Compare the backbone, conditioning, and sampling choices

The model adapts an ESM-2 Transformer into a diffusion Transformer (DiT), comparing Bayesian flow networks (BFN) and discrete flow matching (DFM) on a shared 650M architecture. The studies also examine ways to use MSA conditions: additive profile embeddings, Perceiver cross-attention, and profile initialization for DFM.

The data interface: How is a profile computed?

Four illustrative sequences explain the statistics required by the model. C and T each occur twice at the second position, giving each class a frequency of 0.5.

\[C_{j,a}=\sum_{m=1}^{N}\mathbf{1}[x^{(m)}_j=a],\qquad P_{j,a}=\frac{C_{j,a}}{N}.\]

Here, \(N\) is the number of sequences counted, \(j\) a position, and \(a\) a class. With sequence length \(L\) and \(K\) classes, both the counts and the profile are \(L\times K\) arrays. A profile records only per-position frequencies and cannot by itself express dependencies between positions; generation still relies on the model's sequence context. Training needs \(P\); storing \(C,N\) offline is sufficient to recover it when loading. This interface determines the storage design that follows.

Index once, process in parallel

03 Data processing: Reduce repeated lookup and distribute counting

Computing a profile is straightforward, but repeated lookup, parsing, and token conversion accumulate overhead at scale. The pipeline is divided into stages for optimization: locate first, then compute.

Bottleneck 1 · Repeated lookup

Build an index from record identifiers to storage positions

Scanning from the beginning for every target MSA repeatedly visits unrelated records. An initial scan builds a position index; subsequent retrieval locates the target by its identifier before reading and parsing, reusing the lookup information.

Bottleneck 2 · Large counting workload

Partition targets across multiple CPU nodes

MSA statistics can be computed independently for each target. Split the records into partitions and use multiple CPU servers for lookup, parsing, tokenization, and column-wise counting to produce preprocessed data for training.

Bottleneck 3 · Repeated token conversion

Select the tokenizer implementation through timing comparisons

Time different implementations and select the more efficient approach. Relative to the default implementation, the tokenizer stage was approximately 40% faster; this figure applies to that specific preprocessing stage.

Offline processing for one target · Pseudocode

position = record_index[target_id]
msa_record = read_record_at(position)
aligned_tokens = tokenize(msa_record)
counts, msa_count = aggregate_by_position(aligned_tokens)

Position indexing determines where to read, partitioned parallelism determines who computes, and tokenizer comparisons reduce conversion overhead per record. Once the statistics are computed, another scaling question remains: how should they be stored persistently?

Store counts, normalize on load

04 Storage design: Store integer counts and recover frequencies on use

Because the profile can be recovered from counts and a denominator, compact \(C,N\) values can be stored on disk and normalized to floating point during training data loading. This separates the statistics required by the model from their persistent storage form.

First: Aggregate over MSA depth

Count across \(N\) sequences to aggregate a logical \(N\times L\times K\) array of class indicators into \(L\times K\) counts. When the model uses per-position profiles, the full one-hot expansion need not be stored persistently.

Second: Choose a compact integer representation

Counts are inherently integers. For the same \(L\times K\) shape, a compact integer type covering the count range reduces the bytes per element; conversion to floating point happens when loading.

Table 2 · Representations of an MSA, integer counts, and a floating-point profile
RepresentationLogical shapeInformation retainedRole in the pipeline

Offline storage and training data loading · Pseudocode

# Offline: Store integer counts and the denominator
save_h5(integer_counts=C, msa_count=N)

# Training: Recover the required frequencies after loading
C, N = load_h5(record_id)
profile = to_float(C) / N

The stored values are exact counts. The integer bit width must cover the maximum count, and the class vocabulary and alignment processing rules must remain consistent. The storage change above reflects adjustments to both representation and storage type: the first figure is an initial estimate, while the second is the actual output scale.

What this means for training

Parsing, token conversion, and column-wise counting all happen offline. Training reads and normalizes the counts to use the profile, avoiding repeated computation of the same statistics on every sample access.

From controlled runs to full training

05 Training: Select configurations before full training runs

Once the data is ready, training still needs two things: controlled experiments to select model implementations, and checks that data loading can continuously supply computation. Short experiments use a 150M model before full training at both scales.

Training: Compare how time conditions enter the network

The time variable describes the current noise stage, which a time embedding encodes and injects into the network. Hold other training settings constant, change the time-conditioning implementation, and observe loss and convergence trends at matching step counts to help select a training configuration.

\[e_t=\operatorname{TimeEmbed}(t),\qquad \widehat{x}=f_\theta(x_t,e_t,P).\]

This expression summarizes three inputs: the current generation state \(x_t\), the time condition \(e_t\), and the MSA profile \(P\). Loss comparisons are restricted to the same training objective and loss definition.

Data delivery: Check concurrency settings, rather than only adding workers

Training encountered failures and lower loading efficiency with too many workers, as well as GPU utilization that could not reach the desired level. Storage capacity and runtime data delivery therefore need separate assessment: offline data reduces repeated computation, while concurrent loading still needs adjustment based on observed performance.

Data access, CPU processing, and model computation jointly determine training progress. Completed 150M and 650M training runs are the practical result of this connected data and model pipeline.

Generation: Compare sampling algorithms separately

After model training, iterative sequence generation still requires a choice of sampling method. The sampling studies compare Langevin, ODE, and SDE methods for BFN, alongside settings such as step count and start time. Training loss assesses whether a configuration is learning; generation-stage evaluation assesses candidate performance.

The project evaluates candidates with structural proxy metrics such as pLDDT, pTM, and coevolutionary contact quality. These metrics provide predicted structural evidence; function and real experimental effects still require further validation.

Engineering contributions

06 Connect model design to a working large-scale training pipeline

Model design determines how MSA conditions are used; engineering makes it possible to compute, store, and deliver those conditions to training at scale. The project focuses on connecting the two and using early comparisons to support full training.
